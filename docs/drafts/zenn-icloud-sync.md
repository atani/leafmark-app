個人開発の EPUB リーダーに、iPhone と iPad でハイライトと読書位置が揃う同期機能を入れました。
サーバーは持たず、ユーザー自身の iCloud Drive だけで完結させています。

設計と、途中でユーザーに「データが消えた」と思わせてしまった失敗を書きます。

## 前提となる制約

このアプリはアカウントを作らせません。トラッキングもしません。データは端末内に置きます。
これは機能ではなく、選ばれている理由そのものです。

そのため同期を入れるときも、次の 2 つは崩せませんでした。

- ベンダー側のアカウントを作らせない
- 自分が運用するサーバーを持たない

運用コストの話でもあります。個人開発のサーバーは、落ちたら自分が起こしに行くしかありません。

残る選択肢は、ユーザー自身の iCloud を使うことでした。
CloudKit ではなく iCloud Drive のアプリコンテナを選んでいます。理由は後述します。

## 何を同期して、何を同期しないか

同期するのはハイライト、ノート、ブックマーク、本ごとの読書位置だけです。

EPUB ファイル本体は同期しません。容量の問題もありますが、
取り込み方針として「ユーザーが Files アプリから明示的に入れる」を守りたかったためです。

読書統計と外観設定も同期していません。これらは端末ごとに違うほうが自然だと考えました。
iPad では大きい文字で読み、iPhone では小さい文字で読む人がいます。

## 端末をまたぐキーをどう決めるか

ここが最初の設計上の山でした。

アプリ内では本に UUID を振っています。しかしこれは取り込むたびに新しく振られます。
同じ『フランケンシュタイン』を iPhone と iPad に別々に入れれば、UUID は当然ちがいます。
UUID では突き合わせられません。

そこで EPUB のバイト列の SHA-256 を取り込み時に計算し、これを突き合わせキーにしました。
同じファイルなら別の端末で別々に取り込んでも一致します。

```swift
// 取り込み時にファイルのハッシュを取り、同期の照合キーにする
let contentKey = SHA256.hash(data: epubData)
```

既存の蔵書には初回ロード時にハッシュを計算して移行しました。

同期ドキュメントは本ごとに 1 ファイルです。

```
Documents/Annotations/<contentKey>.json
```

このドキュメントに端末固有の UUID は入れていません。
マージして戻すときに、ローカルの蔵書から付け直しています。

## 衝突をどう解決するか

2 台が同時にオフラインで編集する状況は普通に起きます。飛行機の中で iPad を触り、
降りてから iPhone を触る、というだけで起きます。

レコード単位の last-writer-wins と和集合にしました。

- ハイライトは 1 件ずつ `updatedAt` を持ち、新しいほうが勝つ
- 削除は即座に消さず、墓標として `deletedAt` を書いて伝播させる
- 墓標は 90 日でマージ時に刈る
- 読書位置は単一レコードなので素直に LWW

削除を墓標にしているのは、和集合を取るためです。
単純に消すと、もう一方の端末が「持っている」と主張して復活します。

そしてこのマージ処理を、副作用のない純関数として切り出しました。

```swift
// 入力から出力が決まるだけの関数にしておくと、状況を並べてテストできる
enum AnnotationSyncMerge {
    static func mergeRecords(...) -> ...
}
```

同期のバグは再現が難しく、実機 2 台を並べて手で確かめるのは時間がかかります。
純関数にしておけば、衝突のパターンをテストコードで並べられます。ここは最初にやってよかった点です。

## NSFileVersion の衝突を union-merge で潰す

iCloud Drive は同じファイルが同時に書かれると衝突バージョンを作ります。
通常はどちらを採用するか決める必要があります。

ただしマージ処理が冪等かつ可換であれば、選ぶ必要はありません。
衝突している全バージョンをまとめてマージすれば済みます。

読み書きは NSFileCoordinator 経由にして、リモートの到着は NSMetadataQuery で監視しています。

## CloudKit を選ばなかった理由

CloudKit でもユーザーの iCloud に置けます。実際、多くの場合はそちらが素直です。

iCloud Drive のアプリコンテナにしたのは、保存されるものが
「ユーザーのディスク上の JSON ファイル」であるという説明のしやすさを優先したためです。
スキーマとレコードタイプが、こちら側の管理対象から外れます。

なお `NSUbiquitousContainers` は Info.plist に足していません。
Files アプリに内部ファイルが見えると、ユーザーが触って壊せてしまうためです。

## 失敗した話: 再インストールで「データが消えた」

ここからが本題です。

EPUB 本体を同期しない設計そのものは、今も妥当だと考えています。
ところが、この帰結が利用者にどう見えるかを考え切れていませんでした。

アプリを再インストールすると、次のことが起きます。

1. 端末上の EPUB ファイルは消える
2. 同梱のサンプル本だけが戻ってくる
3. ハイライトは iCloud にあるが、紐づく本がローカルに無いので何も見えない

技術的にはデータは失われていません。同じ EPUB を取り込み直せば、
`contentKey` の一致でハイライトと読書位置が戻ります。

しかし利用者から見れば、蔵書が消えてハイライトも消えています。
そして「同じ本を入れ直せば戻る」ことを伝える手段が、アプリのどこにもありませんでした。

**「データは消えていない」と「消えたように見えない」は別の要件でした。**

対処として、蔵書カタログのメタデータだけを追加で同期しました。ファイルは相変わらず同期しません。

```
Documents/Library/catalog.json
```

中身は `contentKey` とタイトルと著者だけです。これを使って、
カタログにあるがローカルに無い本を「On your other devices」として一覧に出し、
タップするとファイル取り込みが開くようにしました。

マージ処理は注釈用に書いた純関数をそのまま再利用できました。
キーが `contentKey` で、レコード単位 LWW と墓標という構造が同じだったためです。
ここは純関数に切り出しておいた分の利息が返ってきた形です。

## まだ解けていないこと

エンドツーエンドの iCloud 同期は、ヘッドレスで自動検証できていません。
マージ・キー生成・復号互換は単体テストで固めていますが、
実機 2 台の突き合わせは手で確認しています。ここは自動化したいところです。

もう 1 つ、ハッシュを突き合わせキーにした結果として、
同じ本でも配布元が違って 1 バイトでも差があると別の本として扱われます。
実用上は困っていませんが、正しくはありません。

## おわりに

サーバーを持たない同期は、制約が強い代わりに運用がゼロになります。
個人開発では効いてくる性質です。

一方で、同期しないものを決めた結果がユーザーにどう見えるかは、
設計時に想像しきれませんでした。ADR に決定と根拠を書いていても、
その決定が利用者の画面でどう映るかは別に考える必要がありました。

このアプリは [Leafmark](https://apps.apple.com/app/id6781045740) です。
EPUB のハイライトを Markdown へ書き出せる iOS アプリです。読む部分は無料で使えます。
